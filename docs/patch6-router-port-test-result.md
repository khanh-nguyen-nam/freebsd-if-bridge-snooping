## Bug Found: Missing `<sys/types.h>` In The Query Helper

`mdb_router_forward` initially **skipped**: `could not compile mcast_query
helper`. Reproduced the exact compile directly on the VM and got 17 errors, all
`unknown type name 'u_char'`/`'u_short'` from `<netinet/igmp.h>`. That header
uses BSD integer types without including `<sys/types.h>` itself (it relies on
the includer having pulled it in first), and the query helper's source
included `<sys/socket.h>`/`<netinet/in.h>`/`<netinet/igmp.h>` without ever
including `<sys/types.h>`.

**Fix:** added `#include <sys/types.h>` before `<netinet/igmp.h>` in the
`bridge_mdb_compile_query_helper()` heredoc, in three places: the ATF test
script itself (`tests/sys/net/if_bridge_test.sh`), patch `0006`'s corresponding
hunk, and the manual test-plan's Step 2 (same helper source, same bug).

## Bug Found: Missing Multicast Route For The Router Jail

After the include fix, `mdb_router_forward` got past compilation but then
**failed**: `atf-check failed` on `sysctl -n net.link.bridge.mdb_routers`
returning `0` instead of matching `^[1-9][0-9]*$` — the router port was never
learned. `kyua debug` isolated it further to the query helper's own `sendto()`
call failing with `Network is unreachable`.

**Root cause:** `IP_MULTICAST_IF` only selects which interface a multicast
packet should egress from; FreeBSD's `ip_output()` still performs an ordinary
routing-table lookup for the destination first. A freshly created jail's
routing table only has the interface route for its configured `/24`
(`192.0.2.0/24` here) — nothing for `224.0.0.0/4` — so the lookup fails before
the multicast override is ever consulted. The existing topology helpers
already added this route for the **sender** jail (needed for `ping` to a
multicast group), but not for the **router** jail, which patch 6 newly
requires to originate the IGMP query itself.

Confirmed by manually adding `jexec mdbr route add -net 224.0.0.0/4 -interface
<epair>b` before invoking the query helper: `sendto()` then succeeded, tcpdump
showed a well-formed `ttl 1` IGMPv2 query with a valid checksum, and
`net.link.bridge.mdb_routers` read back `1`.

**Fix:** added the same `route add -net 224.0.0.0/4 -interface
${mdb_router_epair}b` call to `bridge_mdb_router_topology_create()` in
`tests/sys/net/if_bridge_test.sh` (and to patch `0006`'s corresponding hunk),
and the equivalent `jexec mdbr route add ...` line to the manual test-plan's
Step 1.

Both fixes were re-verified end-to-end: the full `0001`–`0006` series still
applies cleanly with `patch --batch --forward -p1` against a scratch checkout
of base `97cc6bd98`, and the resulting `if_bridge_test.sh` is byte-identical to
the fixed `freebsd-src` working tree.

Neither bug was in the kernel logic (`bridge_mdb_add_router`,
`bridge_mdb_forward`, the counter, or the aging/cleanup paths) — both were
exclusively in the test scaffolding shipped alongside patch 6.

## Known risk (resolved)

The IGMP-query sender helper uses a raw `IPPROTO_IGMP` socket (kernel builds
the IP header; the 8-byte IGMP body with checksum is supplied by the helper).
This was flagged in advance as the least-certain piece to work first-try on the
VM, and it did in fact need the two fixes documented above (missing
`<sys/types.h>`, missing multicast route) before `mdb_routers >= 1` was
satisfied. Once fixed, `tcpdump -v` on the router jail's interface confirmed a
well-formed `ttl 1` IGMPv2 query with a valid checksum; the kernel
forwarding/learning side is exercised
independently by the manual gating check and does not depend on this helper's
exact framing beyond producing a valid query.
